## Шаг 1. Создание таблицы-полигона (200 000 строк)

Создайте таблицу заказов `orders` и заполните её 200 000 сгенерированными строками с помощью встроенной функции `generate_series()`:

```sql
DROP TABLE IF EXISTS orders CASCADE;

CREATE TABLE orders (
    order_id    SERIAL PRIMARY KEY,
    user_id     INTEGER NOT NULL,
    order_date  TIMESTAMP NOT NULL,
    status      VARCHAR(20) NOT NULL,
    amount      NUMERIC(10, 2) NOT NULL
);

-- Генерация 200 000 строк (занимает 1-2 секунды)
INSERT INTO orders (user_id, order_date, status, amount)
SELECT
    (floor(random() * 2000) + 1)::INTEGER,
    NOW() - (random() * 365) * INTERVAL '1 day',
    CASE
        WHEN gs % 20 = 0 THEN 'cancelled'   -- 5% отмененных
        WHEN gs % 10 = 1 THEN 'paid'        -- 10% оплаченных
        ELSE 'delivered'                    -- 85% доставленных
    END,
    ROUND((random() * 4900 + 100)::NUMERIC, 2)
FROM generate_series(1, 200000) AS gs;

-- Обновляем статистику таблицы для планировщика PostgreSQL
ANALYZE orders;
```

Проверьте количество строк: `SELECT COUNT(*) FROM orders;` (должно быть `200000`).

## Шаг 4. Цена индексов (замер скорости `INSERT`)

Каждый индекс ускоряет чтение (`SELECT`), но замедляет запись (`INSERT`, `UPDATE`, `DELETE`), так как при добавлении строки серверу приходится перестраивать все деревья индексов. Проверим это на практике:

1. Создайте две пустые копии структуры таблицы `orders` — одну без индексов, вторую с тремя индексами:
   ```sql
   DROP TABLE IF EXISTS bench_no_idx;
   DROP TABLE IF EXISTS bench_with_idx;

   CREATE TABLE bench_no_idx AS SELECT * FROM orders WITH NO DATA;
   CREATE TABLE bench_with_idx AS SELECT * FROM orders WITH NO DATA;

   CREATE INDEX idx_b_user   ON bench_with_idx(user_id);
   CREATE INDEX idx_b_date   ON bench_with_idx(order_date);
   CREATE INDEX idx_b_status ON bench_with_idx(status);
   ```

2. Замерьте время вставки 50 000 строк в каждую таблицу:
   ```sql
   EXPLAIN ANALYZE
   INSERT INTO bench_no_idx SELECT * FROM orders LIMIT 50000;

   EXPLAIN ANALYZE
   INSERT INTO bench_with_idx SELECT * FROM orders LIMIT 50000;
   ```
   *Запишите время вставки для обеих таблиц и посчитайте, во сколько раз замедлилась запись.*

3. Удалите временные таблицы после замера, чтобы не занимать лишнее место на сервере:
   ```sql
   DROP TABLE IF EXISTS bench_no_idx;
   DROP TABLE IF EXISTS bench_with_idx;
   ```

## Шаг 5. Частичный индекс (`Partial Index`) и замер размера на диске

В нашей таблице статус `'cancelled'` имеют только **5%** строк. Если мы часто ищем отмененные заказы конкретного пользователя, индексировать оставшиеся 95% доставленных и оплаченных заказов невыгодно.

1. Создайте **частичный индекс** с условием `WHERE status = 'cancelled'`:
   ```sql
   CREATE INDEX idx_orders_cancelled ON orders(user_id) WHERE status = 'cancelled';
   ANALYZE orders;
   ```

2. Сравните размер полного индекса и частичного индекса на диске:
   ```sql
   SELECT
       pg_size_pretty(pg_relation_size('idx_orders_user_id'))   AS full_index_size,
       pg_size_pretty(pg_relation_size('idx_orders_cancelled')) AS partial_index_size;
   ```

3. Проверьте через `EXPLAIN ANALYZE`, что при фильтрации отмененных заказов планировщик выбирает именно новый частичный индекс:
   ```sql
   EXPLAIN ANALYZE
   SELECT * FROM orders WHERE user_id = <my_user_id> AND status = 'cancelled';
   ```
