# Практическая работа #7: Подзапросы и операции над множествами в SQL (WHERE IN, EXISTS, скалярные подзапросы, FROM, UNION, INTERSECT, EXCEPT)

## 1. Цель работы
Освоить продвинутые техники структурирования сложных аналитических запросов в реляционных базах данных с использованием вложенных подзапросов и реляционной алгебры множеств:
1. **Скалярные подзапросы в `WHERE`:** сравнение атрибутов с динамически вычисленным скалярным значением (`=`, `>`, `<`, `>=`, `<=`, `<>`), вычисляемым на лету (например, фильтрация записей с чеком выше среднего по клубу).
2. **Множественные подзапросы в `WHERE` (`IN` и `NOT IN`):** фильтрация строк по принадлежности к динамическому списку ключей из другой таблицы.
3. **Ловушка трехзначной логики (`NULL` в `NOT IN`):** понимание того, почему наличие хотя бы одного значения `NULL` в результатах подзапроса ломает условие `NOT IN` и приводит к пустому результату всего внешнего запроса.
4. **Коррелированные подзапросы (Correlated Subqueries):** подзапросы, зависящие от значений текущей строки внешнего запроса, и сценарии их применения.
5. **Предикаты существования (`EXISTS` и `NOT EXISTS`):** эффективная проверка наличия связанных записей без выгрузки данных в память и безопасная замена `NOT IN`.
6. **Подзапросы в секции `SELECT`:** расчет скалярных аналитических колонок (LTV, количество сессий, сумма заказов) индивидуально для каждой строки витрины.
7. **Производные таблицы в секции `FROM` (Inline Views / Derived Tables):** расчет «агрегатов над агрегатами» (например, среднее число заказов на одного клиента, дисперсия выручки).
8. **Операции над множествами:**
   * `UNION` — объединение наборов с удалением дубликатов;
   * `UNION ALL` — быстрое объединение без дедупликации;
   * `INTERSECT` — пересечение множеств (поиск объектов, присутствующих в обоих источниках);
   * `EXCEPT` — разность множеств (поиск объектов из первого запроса, отсутствующих во втором).
9. **Архитектурный выбор:** четкое понимание, в каких случаях эффективнее использовать `JOIN`, в каких — подзапрос `WHERE IN / EXISTS`, а в каких — табличное выражение в `FROM`.

## 3. Лекторский минимум и золотые правила подзапросов

```
                     ┌───────────────────────────────────────────────┐
                     │          АНАТОМИЯ ПОДЗАПРОСОВ В SQL           │
                     └───────────────────────────────────────────────┘
                                             │
         ┌───────────────────────────────────┼──────────────────────────────────┐
         ▼                                   ▼                                  ▼
  ┌───────────────┐                   ┌───────────────┐                  ┌───────────────┐
  │   В SELECT    │                   │    В WHERE    │                  │    В FROM     │
  │ (Вычисленная  │                   │ (Фильтрация   │                  │ (Производная  │
  │   колонка)    │                   │   по условию) │                  │   таблица)    │
  └───────────────┘                   └───────────────┘                  └───────────────┘
         │                                   │                                  │
  Строго 1 строка                     ┌──────┴──────┐                    Обязателен
  и 1 колонка                         ▼             ▼                    псевдоним AS!
                              Скалярный       Множественный
                             (=, >, <, <>)    (IN, EXISTS)
```

1. **Правило скалярности в `SELECT` и сравнениях:**  
   Если подзапрос стоит в секции `SELECT` или после операторов `=`, `>`, `<`, он обязан возвращать **строго одну строку и один столбец**. Если подзапрос вернет 2 строки или 2 столбца, СУБД вернет фатальную ошибку (`subquery returns more than 1 row`).
2. **Коварная ловушка `NOT IN` и `NULL`:**  
   В SQL выражение `x NOT IN (1, 2, NULL)` логически раскрывается как:  
   `x <> 1 AND x <> 2 AND x <> NULL`.  
   Поскольку любое сравнение с `NULL` дает `UNKNOWN`, всё логическое выражение превращается в `UNKNOWN`, что в `WHERE` трактуется как `FALSE`.  
   **Следствие:** если во внутреннем запросе `SELECT member_id FROM ...` окажется хотя бы один `NULL`, весь запрос `WHERE member_id NOT IN (...)` вернет **ноль строк**!  
   **Правило безопасности:** при отрицании всегда используйте `NOT EXISTS` либо явно отфильтровывайте `WHERE member_id IS NOT NULL` во внутреннем запросе.
3. **Обязательный псевдоним в `FROM`:**  
   Любой подзапрос в секции `FROM` обязан иметь псевдоним (например, `FROM (...) AS sub`), иначе запрос не скомпилируется.
4. **Правила операций над множествами (`UNION`, `INTERSECT`, `EXCEPT`):**  
   * Количество столбцов во всех объединяемых запросах должно быть одинаковым.
   * Типы данных и смысловое назначение столбцов на соответствующих позициях должны совпадать.
   * `UNION` автоматически производит сортировку для удаления дубликатов; если дубликаты допустимы или гарантированно отсутствуют, используйте более быстрый `UNION ALL`.
